# Charter attestation decoder, a paid x402 agent

One capability: decode the charter payload of a Base EAS attestation from its raw data. The caller
sends the bytes, the agent returns the version, the date, the text names, their sha256 digests and
their IPFS CIDs. Nothing is read from the network, so every answer is a pure function of the request
and a buyer can check it against the chain and the files themselves.

## Live endpoint

```
POST https://0ed1100ce8a700.lhr.life/v1/charter
GET  https://0ed1100ce8a700.lhr.life/health
```

This is a tunnel hostname on a small VPS, so it can change; the code in this repository is the same
server. Verified from the public internet: `/health` answers 200, and an unpaid POST answers 402 with
the x402 terms, `maxAmountRequired` 10000 (0.01 USDC), `network` base, `scheme` exact, `payTo` the
agent wallet.

Price per call: 0.01 USDC on Base.

## Call it

```bash
curl -sS -X POST https://0ed1100ce8a700.lhr.life/v1/charter \
  -H 'content-type: application/json' \
  -d '{"capability":"charter.parse","input":{"data_hex":"0x..."}}'
```

Unpaid, the answer is 402 with `PAYMENT-REQUIRED` and the terms in the body. Paid, the answer is the
decoded payload.

## How a payment is actually taken

The public x402 facilitator only settles testnets, so this agent settles on its own with a relayer
key: it recovers the payer from the EIP-712 signature, refuses a nonce that is already used on chain,
submits `transferWithAuthorization` itself, and only answers after the receipt is successful. The
settlement transaction comes back in the answer and in the `X-PAYMENT-RESPONSE` header.

Proven twice, on chain, not claimed:

```
0x216f958d2625010d934e5783ecd69a041da15950c5249de2e4019a8b9d52d609   local run, block 53131145, status 1
0x19d448a80471c9a92bdc9be91bc3eca072fbf68d303104e77b98cbda2b68696b   through the public endpoint, status 1
```

A third settlement came through the public endpoint for `charter.verify`, answering 200 with the
attestation fields of a real Base UID.

Both are 10000 atomic USDC transfers. They are self payments between the agent's own wallet, which is
what a test is; the code path is the same one a buyer's payment takes.

## Two capabilities

`charter.parse` takes `data_hex` and decodes the tuple. `charter.verify` takes `uid` and an optional
`network` (8453 or 84532), fetches the attestation from EAS over RPC, decodes the charter payload and
checks every text against its sha256 digest by fetching it from IPFS.

```bash
curl -sS -X POST $ENDPOINT -H 'content-type: application/json' \
  -d '{"capability":"charter.verify","input":{"uid":"0x..."}}'
```

## A refusal never costs the caller

The handler validates the capability and the input **before** it asks for payment, so a wrong uid or a
malformed payload answers 400 with no settlement at all. This was not always true: an earlier build
settled first and answered 400 second, and one test payment was spent on a refusal. The order was
reversed and this is checked from the public endpoint with three malformed requests that all answer
400 while carrying a payment header.

## What it refuses

- A capability it does not have: 400 with the list of the ones it does.
- `input.data_hex` that is not 0x hex: 400.
- Bytes that do not decode as the charter tuple: 422 with the reason, rather than a guess.
- A payment it cannot verify: 402, never a free answer.

It also refuses to judge: it reports what the bytes contain, never whether a charter is legitimate.

## The registry offer

`lax-offer.json` is the offer as it is meant to be listed: name, description, endpoint, the
capability with an input schema, an output schema and a price per call, and the five laws stated in
the offer's own words. `test/agent.test.mjs` checks the fields against the section schema fetched from
`https://lax.kognai.ai/aiax/sections/lax_offer.json`, including that the endpoint is https and not on
kognai.ai.

## Tests, named after the acceptance items

```bash
node --test test/agent.test.mjs
```

- A1 the offer carries the registry fields and passes a local validation.
- A2 every capability has an input schema, an output schema and a price per call.
- A3 the three examples are real calls that match the schemas.
- A4 an unpaid call answers 402 with the terms, a paid one is decoded, a refused payment stays 402.
- A5 the buyer's three paid test calls; offline there is nothing to assert, so it is marked done only
  when that happens.

Seven tests, all passing. The examples under `examples/` are generated by calling the agent from the
test, not written by hand, so they cannot drift from the code.

## Files

```
server.js              the agent, the 402 terms and the handler
lib/charter.js         the ABI decoder (no dependency)
lax-offer.json         the offer as listed
examples/*.json        request and response pairs produced by the agent
test/agent.test.mjs    A1 to A5 plus the encoder used to build a payload
```

The encoder in the test exists only to produce a payload to decode; it writes the same tuple the
on chain attestations use, with the offset table the arrays need. Two things it taught me: an array
of strings carries relative offsets rather than inline lengths, and the decoder returns digests with a
0x prefix.
